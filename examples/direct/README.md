# WebRTC-Direct examples: STUN, TURN, and the sidecar

Runnable examples for the generated gRPC runtimes talking over
**WebRTC-Direct**: a peer listens on a UDP socket and prints a
*certhash multiaddr* (`/ip4/.../udp/.../webrtc-direct/certhash/f...`);
a client dials that address and gets a DTLS/SCTP DataChannel carrying
plain gRPC frames. No signaling server, no SDP exchange.

Files (per-language examples are generated by
grpc-dc codegen; do not edit them by hand):

| File | What |
|---|---|
| [server.mjs](server.mjs) / [client.mjs](client.mjs) | Node Echo server/client on a Direct listener; direct dial, or via TURN with `DIRECT_TURN` set |
| `go/examples/direct_echo` | Go server/client, embedded stack: `serve`, `dial`, plus full-ICE `peer-serve`/`peer-dial` (STUN) |
| `rust/examples/direct_echo.rs` | Rust server/client, embedded stack: same four modes (`cargo run --features webrtc --example direct_echo`) |
| [python_client.py](python_client.py) / [python_server.py](python_server.py) | Python Echo through the Rust `direct_sidecar` |
| `<lang>/examples/direct_echo.*` | serve/dial Echo for Ruby, PHP, Lua, C, C++, Dart, Java, Kotlin, Scala, Swift, C#, Zig — all through the sidecar; build/run commands are in each file's header |
| [docker-compose.yml](docker-compose.yml) | servers + clients + a real coturn; `host`, `go`, `turn`, `stun`, and `sidecar` profiles; servers write the multiaddr (or peer SDP) into a shared `/signal` volume and clients wait for it there |

## Quick start (host, no TURN)

```sh
node examples/direct/server.mjs
# MULTIADDR /ip4/127.0.0.1/udp/51819/webrtc-direct/certhash/f...
# (port is ephemeral unless DIRECT_PORT is set; DIRECT_ADDRESS and
#  DIRECT_PORT env vars pin the bind for containers/LAN use)

node examples/direct/client.mjs '/ip4/127.0.0.1/udp/51819/webrtc-direct/certhash/f...'
# mode: direct (no TURN)
# unary -> echo: hello direct
# direct-echo OK
```

Or with compose (servers publish their multiaddr into the shared
`/signal` volume; clients pick it up automatically):

```sh
docker compose -f examples/direct/docker-compose.yml up js-server
docker compose -f examples/direct/docker-compose.yml --profile host run --rm js-client
docker compose -f examples/direct/docker-compose.yml --profile go run --rm go-client
docker compose -f examples/direct/docker-compose.yml --profile sidecar run --rm python-client
```

## With TURN

TURN is a **client-side** tool here: a client behind a symmetric NAT
allocates a relay on a TURN server and dials the Direct listener
*through the relay*. The server never changes and does not need to
know TURN exists.

```sh
docker compose -f examples/direct/docker-compose.yml --profile turn up turn
DIRECT_TURN=127.0.0.1:3478 DIRECT_TURN_USER=grpc DIRECT_TURN_PASS=grpc \
  node examples/direct/client.mjs '/ip4/...'
# mode: turn (allocation via 127.0.0.1:3478)

# or fully in compose (Go TURN client shown; js-client-turn also exists):
docker compose -f examples/direct/docker-compose.yml --profile turn run --rm go-client-turn
```

One JS caveat: the JS TURN dialer matches TURN replies by sender
address, so `DIRECT_TURN` must be an IP literal (`127.0.0.1:3478`),
not a hostname. The compose TURN clients resolve `turn` to its
container IP for exactly this reason. Go and Rust accept hostnames.

Local-testing note: coturn refuses to relay to loopback/private peers
by default (SSRF protection). For a same-machine test add
`--allowed-peer-ip=127.0.0.1` (and your LAN range) to the coturn
command, as the compose `turn` profile does. Do not do that on a
public TURN server.

## Where STUN fits

A Direct listener binds a plain UDP socket; it does not gather ICE
candidates, so STUN is not part of dialing a multiaddr. STUN is used
by the *full-ICE* peer APIs (browser `RTCPeerConnection` and the
native stacks' peer mode), where it discovers server-reflexive
candidates for NAT traversal. The Go and Rust examples include that
mode — SDP is exchanged through files in `GRPC_DC_SIGNAL_DIR`
(a stand-in for any signaling channel):

```sh
GRPC_DC_STUN=stun.l.google.com:19302 go run ./examples/direct_echo peer-serve
GRPC_DC_STUN=stun.l.google.com:19302 go run ./examples/direct_echo peer-dial
# or: docker compose -f examples/direct/docker-compose.yml --profile stun run --rm go-peer-client
```

Add `DIRECT_TURN*` in peer mode to also gather a TURN relay
candidate. If the Direct listener sits behind a NAT, the usual
answers are a port forward, a public-IP host, or the TURN dial
above — STUN alone cannot make an inbound UDP listener reachable.

## Browsers and TURN

Browsers have no UDP sockets, so a browser page can never dial a
multiaddr. Browser clients join through full ICE with a native peer
(the browser examples), where the browser's own `RTCPeerConnection`
does STUN/TURN natively. Two honest limits:

- A browser behind a symmetric NAT needs the **native peer** to be
  reachable (public IP or its own TURN relay); a TURN server for the
  browser side is configured in the page's `iceServers`, which the
  browser examples accept.
- The `cloudflared` quick-tunnel used by the browser examples is
  TCP-only: it cannot carry TURN/UDP or a Direct listener. Browser +
  tunnel + TURN together are not supported; run the native peer on
  the same LAN or on a public host instead.

## Other languages (the sidecar)

Only JS, Go, and Rust embed the WebRTC stack. Every other generated
runtime (Python, Ruby, PHP, C, C++, Dart, Lua, Zig, …) reaches
WebRTC-Direct through its generated `SidecarTransport` plus the Rust
`direct_sidecar` bridge:

```sh
cargo build --manifest-path webrtc/rust/Cargo.toml --example direct_sidecar
webrtc/rust/target/debug/examples/direct_sidecar dial \
  --multiaddr '/ip4/.../webrtc-direct/certhash/f...' --tcp 127.0.0.1:50061
python3 examples/direct/python_client.py 127.0.0.1:50061
```

Add `--turn host:port --turn-user USER --turn-pass PASS` to the
sidecar dial for the TURN path; the language code is identical.
Every language ships this as a generated `direct_echo` example with
`serve` and `dial` modes (paths in the file table above; build/run
commands in each file's header), and the same transport is exercised
for every language by the generated BDD sidecar tests in CI.

## Modes at a glance

| Mode | Client path | Server requirement | Works from a browser? |
|---|---|---|---|
| direct (host/LAN) | UDP dial of the multiaddr | reachable UDP port | no (no UDP in browsers) |
| direct + TURN | TURN allocation → relayed UDP dial | reachable UDP port | no |
| full ICE + STUN | ICE with STUN-discovered candidates | native peer (any stack) | yes — this is the browser path |
| full ICE + TURN | ICE with relay candidates | native peer | yes, `iceServers` in the page |
